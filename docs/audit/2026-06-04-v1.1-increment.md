## 2. 干净项（正向比对）

- **迁移数据安全**：先写 IDB→确认 put resolve→再删旧 key；UT-MIG-003 验证 put 失败时**不删旧 key**（数据不丢）；UT-MIG-002 验证幂等（IDB 有值跳过迁移）
- **hydrate 竞争防护**：`if (stored && state.text() === '')` 防止异步还原覆盖用户在加载窗口内的输入（数据丢失 race，已挡）
- **写值时机**：performWrite `const value = text()` 在 await 前捕获 → 不受 await 期间信号变化影响
- **契约对齐**：api-spec v1.1（移除同步 init / clear→Promise / loadStoredDocument）与实现一致
- **upgrade 幂等**：`if (!contains(STORE)) createObjectStore` 防重复建
- **bundle**：idb +1.5KB → 66.08KB gz（<150 闸）；fake-indexeddb 仅 dev，未入 src
- **fallback 后端**：IDB 不可用 → localStorage + degraded toast，读/写/清三操作一致落 localStorage（UT-FALLBACK-004/006）

## 3. 发现

| 编号 | 单元 | 描述 | severity |
|------|------|------|---------|
| F-V11-1 | `loadStoredDocument` catch | **IDB 读错静默降级**：catch 直接返回 localStorage fallback（IDB 用户的 localStorage 已空）→ 显示空文档、**无任何错误信号/日志**。罕见 IDB 读损坏 → 用户感知"数据丢失"；若此时用户编辑，write-back 会用新内容覆盖 IDB 中仍在的旧文档 → **真数据丢失**。建议：catch 加 `console.error`；区分"IDB 空"（正常）vs"IDB 读 throw"（异常，不应静默当空）| **MEDIUM** |
| F-V11-2 | `_storage.ts` resetStorage | `indexedDB.open('editor')` **无 version**：若先于 app 的 `openDB(1,{upgrade})` 跑 → 创建 v1 无 kv store 的 DB → app openDB(1) 不触发 upgrade → kv 缺失 → app 失败。当前靠 app 先创建赢竞争（e2e 33 绿），latent flaky | LOW (test-infra) |
| F-V11-3 | `store.ts` clear catch | clear 的 IDB delete 失败静默吞（best-effort），无 log（同 F-V11-1 的轻量版）| LOW |
| F-V11-4 | `main.tsx` + store | 每次加载 hydrate `setText(stored)` 触发 effect → debounce 写回同值到 IDB（幂等无害但多一次 IDB 写 + status IDLE→DIRTY→SAVING→IDLE 抖动）| LOW |
| F-V11-5 | `zh-CN.dict.ts` | `storage.unavailable` key 无消费方（v1.0 起即未用 / 死 key）| LOW |
| F-V11-6 | `store.ts` performWrite | 异步写理论可重叠（debounce 间隔短 + IDB 慢时）；last-write-wins 但 status 短暂错乱。极边缘 | LOW |

### arch-constraints 关联

F-V11-1/F-V11-3 触及 §8（异步 catch 须 log）/§9（不裸吞异常）。本项目是 FE SPA 无后端日志层，等价要求 = `console.error`；当前异步 catch 静默 → 违背"不裸吞"精神。

## 4. 盲点声明

- **F-V11-1 的"真数据丢失"是推断链**（IDB 读 throw → 显空 → 用户编辑 → write-back 覆盖），未实测构造 IDB 读异常复现；severity MEDIUM 基于该链的后果严重度，非高频
- **F-V11-2 未实测竞争翻车**（e2e 一直绿）；属"读代码看出的 latent race"
- **未跑增量专属 e2e 回归**：依赖 v1.1 实现期已跑的 unit 120 + e2e 33

## 5. 结论

迁移核心逻辑（幂等 + 数据安全 + 竞争防护）**正确且有测试佐证**，无 critical/high。但有 **1 条 MEDIUM（F-V11-1 静默降级 + 潜在覆盖丢数据）** 值得在 tag v1.1.0 前修——它是数据安全语义，比纯 UX 重。

**建议：** F-V11-1（catch 加 log + 区分读错 vs 空）+ F-V11-2（resetStorage 用带 version+upgrade 的 open）在 v1.1.0 发布前修；F-V11-3~6 可 deferred。
