# FB 候选 — perf 测量保真度：测量优先 + 合成负载须贴近真实交互路径

- **来源项目：** editor
- **触发场景：** perf 压测 4 条「未压测」finding（BHV-008 / F-V14-1 / F-V16-5 / F-V18-1）
- **日期：** 2026-06-09
- **提交者：** chenrui

## 问题描述

压测一轮里连踩两类 perf 测量陷阱：

1. **假设驱动归因（未测先信）：** BHV-008 假设「行号 gutter 放大大文档成本」。直接测：5000 行/374KB 文档 gutter ON 378ms vs OFF 374ms（等价）——gutter 根本不是瓶颈。若不测直接「优化 gutter」=纯白做。逐层拆解才定位真瓶颈：preview 每键同步全量重渲染。

2. **合成负载伪影（负载形态≠真实交互）：** 测大文档输入延迟，用合成「全量 `textarea.value=` 替换」测出 539ms——其中 176–236ms 是浏览器原生「整串替换 374KB」的成本，真实增量打字根本不走这条路。改用 `execCommand('insertText')` 增量插入（贴近真实键入）得真实 **17ms/键**。信第一组数 → 会误判防抖无效 / 瓶颈错位。

3. **附带两个量纲混淆：** ① dev（未压缩）render 耗时远高于 prod，绝对值不能当 SLA；② 同步阻塞 vs 异步/deferred 成本要分开量（mermaid 同步只 +3ms，真实开销是异步重渲的闪烁/CPU）。

## 模式识别

这是 perf 测量**方法论**层面的规律性陷阱，非单 bug，跨项目通病：测量负载的形态/环境若不贴近真实，会系统性误导优化方向。与 FB-006（功能验证的认知陷阱：看到「不生效」先质疑验证方式）同属「测量/验证保真度」meta 家族，但维度不同——FB-006 管功能对错/生效与否，本条管性能快慢/瓶颈定位。FB-006 的 guidance 不覆盖 perf 场景。

## 建议方向

standard 增 perf 测量原则（可并入 testing 指南或新开 perf 段）：

1. **测量优先于优化**：动手前先用数据证明瓶颈，禁「假设驱动优化」。
2. **合成负载须贴近真实交互路径**：增量 vs 全量、冷加载 vs 热、真实事件 vs 程序模拟——形态对了数才可信。
3. **分清三类成本**：同步阻塞 / 异步 deferred / 后台 CPU 浪费，分别量，别混成一个数。
4. **dev≠prod 显式标注**：dev 绝对值不当 SLA，用相对量级 + 架构判断下结论。
5. **每条 perf finding 收口二选一**：数据证明没事→带数据 dismiss；确认真问题→优化+再测。
